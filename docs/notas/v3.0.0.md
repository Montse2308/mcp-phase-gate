# mcp-phase-gate 3.0.0

*Published on npm on 2026-10-17. In Spanish: [Español](#español).*

The first major version. The flow adapts to the kind of work through **presets**, each project declares its own configuration, and **the server writes phase 4**: the AI hands it the data of each batch, and the server writes the receipt, checks the commit against git and closes the phase.

**There was no 3.0.0-beta on npm.** A `3.0.0-beta.0` was prepared on 2026-10-15 (commit `bfe2c5b`) to be published with the `beta` tag, but it never was: `npm view mcp-phase-gate@3.0.0-beta.0` answers 404, and no tag for it was ever pushed. 3.0.0 is the first 3.x on npm.

## What's in it

- **Per-project configuration.** A `phase-gate.json` manifest in each project's folder (preset, repos, rules), and a `machine.json` per machine (where each repo lives there, default preset). A badly written manifest is an error that names the exact path of the problem, never a silent fall back to the defaults.
- **Presets.** `software` (the new default), `software-replica` (the 2.x flow, byte for byte), `software-tdd`, `multi-repo-feature`, `ai-agent-ops` and `research-ops`. A preset is a single file of blocks.
- **Layers and blocks for the prompts.** The packaged prompts, the preset, the rules, your global layer and the project's are stacked, and a block changes one slot of a prompt without copying it. The packaged prompts moved to `prompts/es/`.
- **`init` and `eject`.** `init` registers the server in Claude Code, Cursor and VS Code and migrates projects; `eject` copies a prompt, a slot, a command or a preset so you can edit it.
- **Several repositories.** `read_repo_file` and `repo_status` work on the repos a manifest declares, by id, and the project is deduced from the folder the client has open (MCP Roots).
- **The server writes phase 4.** `record_batch` and `get_batch_status`. Each receipt is anchored to a commit on the branch, to the sha256 of a file, or to a note, and a receipt with a commit or a sha256 is **sealed**: it can be re-anchored (`reanclar`) after a rebase, but not rewritten. When the last batch is anchored the server generates `04 - Execution.md`, and phase 5 receives the commits already verified.
- **`doctor`** shows the presets, manifests, repos, roots and where each slot of a prompt comes from, and checks receipts, anchors and indices (`doctor --reverificar` also checks against git).

## What changes if you upgrade from 2.x

**The default preset is no longer the replica flow** (`software-replica`) but the generic `software`. If your projects worked with the replica, three steps keep exactly what you had:

1. **Update.** Via `npx` it arrives on its own. From source: `git pull`, `npm install` and `npm run build`.
2. **Choose your preset.** To carry on as before in all your projects without a manifest, one of two:
   - `npx mcp-phase-gate init --migrate` writes `phase-gate.json` with `"preset": "software-replica"` in every project that lacks one (it only creates, never overwrites), together with the project's `idioma`. It travels with the documentation.
   - `npx mcp-phase-gate init --migrate --solo-este-equipo` writes `"presetPorDefecto": "software-replica"` into this machine's `machine.json`, without touching the documentation. Repeat it on each machine.

   If you do nothing, your projects use `software`: the same flow, with verification and testing aimed at code with or without a suite, and no replica.
3. **Check it** with `npx mcp-phase-gate doctor`: the `PRESET-IMPLICITO` finding (a project without a manifest on the default preset) goes away, and each project states its preset. `doctor --fase 3 --proyecto <NAME>` shows where each section of the prompt comes from.

What else changes, in case it affects you:

- **The packaged prompts moved to `prompts/es/`** (and, since 3.2, `prompts/en/`). Your `PHASE_GATE_PROMPTS_PATH` stays as it is: your own layers keep their files at the root.
- **A `global-rules.md` of your own** now gets the packaged `BASIS OF EACH DECISION` and `INHERITED PENDING ITEMS` sections (or their Spanish versions) if it lacks them. Better still: replace it with a `bloques.md`.
- **`project` is optional** in the tools that required it, if your client announces the open folder. If you already pass it, nothing changes.
- **Four new tools**: `read_repo_file` and `repo_status`, for the repos a manifest declares, and `record_batch` and `get_batch_status`, with which the server writes and verifies phase 4. `read_cross_repo` stays as it is.
- **The server writes phase 4.** The AI no longer writes receipts or the phase 4 document with `write_central_doc` (they're refused): it records each batch with `record_batch`. A task halfway through carries on from the next batch.

### Qué trae

- **Configuración por proyecto.** Un manifiesto `phase-gate.json` en la carpeta de cada proyecto (preset, repos, reglas), y un `machine.json` por equipo (dónde está cada repo allí, el preset por defecto). Un manifiesto mal escrito es un error que dice la ruta exacta del problema, nunca una caída en silencio a los valores por defecto.
- **Presets.** `software` (el nuevo por defecto), `software-replica` (el flujo de la 2.x, byte por byte), `software-tdd`, `multi-repo-feature`, `ai-agent-ops` y `research-ops`. Un preset es un solo archivo de bloques.
- **Capas y bloques para los prompts.** Se apilan los prompts de fábrica, el preset, las reglas, tu capa global y la del proyecto, y un bloque cambia una ranura de un prompt sin copiarlo. Los prompts de fábrica se mudaron a `prompts/es/`.
- **`init` y `eject`.** `init` registra el servidor en Claude Code, Cursor y VS Code y migra proyectos; `eject` copia un prompt, una ranura, un comando o un preset para que lo edites.
- **Varios repositorios.** `read_repo_file` y `repo_status` trabajan sobre los repos que declara un manifiesto, por id, y el proyecto se deduce de la carpeta que el cliente tiene abierta (MCP Roots).
- **El servidor escribe la Fase 4.** `record_batch` y `get_batch_status`. Cada recibo se ancla a un commit de la rama, al sha256 de un archivo o a una nota, y un recibo con commit o sha256 queda **sellado**: se puede reanclar (`reanclar`) después de un rebase, pero no reescribir. Al anclar el último lote el servidor genera `04 - Ejecución.md`, y la Fase 5 recibe los commits ya verificados.
- **`doctor`** enseña los presets, los manifiestos, los repos, las raíces y de dónde sale cada ranura de un prompt, y revisa recibos, anclas e índices (`doctor --reverificar` comprueba además contra git).

### Qué cambia si actualizas desde la 2.x

**El preset por defecto deja de ser el flujo de la réplica** (`software-replica`) y pasa a ser `software`, genérico. Si tus proyectos trabajaban con la réplica, en tres pasos conservas exactamente lo de antes:

1. **Actualiza.** Por `npx` llega solo. Desde el código: `git pull`, `npm install` y `npm run build`.
2. **Elige tu preset.** Para seguir como antes en todos tus proyectos sin manifiesto, una de dos:
   - `npx mcp-phase-gate init --migrate` escribe `phase-gate.json` con `"preset": "software-replica"` en cada proyecto que no lo tenga (solo crea, nunca sobrescribe), junto con el `idioma` del proyecto. Viaja con la Documentación.
   - `npx mcp-phase-gate init --migrate --solo-este-equipo` escribe `"presetPorDefecto": "software-replica"` en el `machine.json` de este equipo, sin tocar la Documentación. Repítelo en cada equipo.

   Si no haces nada, tus proyectos usan `software`: el mismo flujo, con la verificación y las pruebas pensadas para código con o sin suite, sin la réplica.
3. **Compruébalo** con `npx mcp-phase-gate doctor`: el aviso `PRESET-IMPLICITO` (un proyecto sin manifiesto que usa el preset por defecto) desaparece, y cada proyecto dice su preset. `doctor --fase 3 --proyecto <NOMBRE>` te enseña de dónde sale cada sección del prompt.

Qué más cambia, por si te afecta:

- **Los prompts de fábrica se mudaron a `prompts/es/`** (y, desde la 3.2, `prompts/en/`). Tu `PHASE_GATE_PROMPTS_PATH` sigue igual: las capas propias tienen sus archivos en la raíz.
- **Un `global-rules.md` propio** recibe ahora las secciones `BASE DE CADA DECISIÓN` y `PENDIENTES HEREDADOS` de fábrica (o sus versiones en inglés) si no las trae. Mejor aún: cámbialo por un `bloques.md`.
- **`project` es opcional** en las tools que lo pedían, si tu cliente anuncia la carpeta abierta. Si ya lo pasas, nada cambia.
- **Cuatro tools nuevas**: `read_repo_file` y `repo_status`, para los repos que declara un manifiesto, y `record_batch` y `get_batch_status`, con las que el servidor escribe y verifica la Fase 4. `read_cross_repo` sigue igual.
- **La Fase 4 la escribe el servidor.** La IA ya no escribe recibos ni el documento de la Fase 4 con `write_central_doc` (se rechazan): registra cada lote con `record_batch`. Una tarea a medio camino sigue desde el siguiente lote.
