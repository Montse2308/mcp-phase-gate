## UNBREAKABLE GLOBAL RULE (ZERO BREAKAGE)
- Never modify existing logic, components, or functions unless it is 100% necessary. If changing something that already exists could break another part of the system that uses it, STOP.
- Outside Phase 4, if you need to change existing code or make an architecture decision, ask the user first. In Phase 4, the approved technical plan IS that authorization for the changes it lists; ask only about what the plan does not cover.
- When you propose a change, you MUST explain in detail why it is needed and what it implies for the rest of the system, so the user can understand it and approve it.

## EVIDENCE
Every claim is anchored in something another person can open and check:
- the `file:line` of the code, configuration, or prompt that backs it; or
- the actual output of something you ran (a command, a query, a test), with what was run and when.

Whenever this workflow says `file:line`, it means this unit of evidence.

## BASIS OF EACH DECISION

Every decision `D<n>`, whichever phase it is born in, states the basis on which it is recommended or closed:

- **Basis:** `measured (<what was run and against what> · validity: <data window | commit | version | date>)` | `read in code (<file:line>)` | `documented (<source or URL>, <date or version>)` | `inferred (<what would confirm or refute it>)`

Rules for the Basis:
- `measured` requires a source and a validity. A measurement whose source you did not confirm is current —a replica whose freshness you did not check, a model or environment different from the real one— is `inferred`, not `measured`. Measuring against stale data and calling it a measurement is worse than not measuring.
- `documented` is documentation with a source and a date or version. It is no substitute for reading the code when the code exists.
- `inferred` is a legitimate basis, not a defect. But it has to say what would confirm or refute it, so the next phase knows what to measure.
- If a decision rests on several bases, declare the weakest one: it is the one that governs how much to trust it.

### DELIVERY (mandatory)
Deliver the COMPLETE description inside ONE SINGLE code block fenced with

### TITLE
Format: `type(area): phrase`
- `type`: feat | fix | refactor | perf | chore
- `area`: the affected module, report or screen, in English and lowercase
- `phrase`: what the change achieves, lowercase, no trailing period, at most 80 characters
- The title ends there. Do NOT add a ticket number, or `- #NNNN`, or references

### BLOCK 1 — WHY (always)
Pick the heading with this rule, not by taste:
- `## Problem` — if something was broken or returned wrong data. Say what
  was wrong and, if known, how it was detected (who reported it, in which
  period, how big it was).
- `## Context` — if it is new functionality or an improvement, not a defect.
  Say what was missing and why it is needed.
- No heading, 1 or 2 lines of running text — if the change is trivial (up to
  three dimensions touched). Even when trivial, say what was wrong or what was
  missing, not just what you did.

Length: 1 to 4 lines. NEVER open the description with a list.

### BLOCK 2 — CHANGES (always)
Heading `## Changes`. Grouped bullets.

Exception for trivial changes: 2 or 3 bullets in a flat list and WITHOUT the
`## Changes` heading, hanging directly from the opening paragraph. The rules
for each bullet still apply in full.

Pick the grouping criterion with this table, based on the shape of the change:

| If the change is...                                | Group by            |
|----------------------------------------------------|---------------------|
| One point touched, many consumers affected         | affected surface    |
| Several components or layers                       | component           |
| A new feature with several parts                   | sub-feature         |
| A fix that repairs several facets of the same data | data dimension      |
| Two independent pieces of work in one PR           | numbered 1. / 2.    |
| Five bullets or fewer                              | flat list           |

Rules for each bullet:
- Open with a short label in **bold** followed by a colon.
- It MUST say what it does now AND what it did before (or why it was needed). A
  bullet that only describes the new state is incomplete: rewrite it.
- At most 3 lines per bullet, at most 6 bullets per group, at most 4 groups.

### BLOCK 3 — CLOSING (conditional)
Include ONLY the sections whose condition is met. If none is met, the
description ends at Changes.
- `## Scope` — if you touched existing code that other parts consume. Say
  explicitly what did NOT change and which flows are not affected.
- `## Verification` — ONLY if you did a substantial verification: comparing
  against real data, measuring, running over a volume. Write it in the past
  tense and with numbers. If you only tested it by hand locally, OMIT this
  section entirely.
- `## Deployment notes` — if there are migrations, a deployment order or
  something to know when deploying. In large PRs with none of that, a single
  line: "No migrations; code only."
- A standalone `**Note:**` at the end — if there is a visible change in
  behavior that the user will notice without anyone telling them.

In trivial changes, if any of these applies, it goes on a single line with the
label in bold (`**Scope:** ...`) instead of as a section heading.

### LENGTH (count the words, do not estimate them)
- Trivial: 55-90 words. Title + 1 or 2 lines of why + 2 or 3 bullets.
- Small: 110-150 words
- Normal: 190-240 words  ← default target
- Large: 320-400 words. Hard cap: 450.

If you go over the cap, do NOT cut the why: remove detail bullets.

### FORBIDDEN
- Putting a ticket number or `#NNNN` references in the title.
- Listing file by file. (Naming a file is fine when that file IS the center

### Example A — normal size (~215 words), grouped by dimension

--- BEGIN EXAMPLE ---
feat(gift cards): add an internal note and record it in the order history

## Context
When issuing a gift card there was a single "Message" field, and that text is printed on the card the customer receives. Support had no way to leave its own note on why a card was issued, nor to see it in the order history.

## Changes
- **Issue form:** adds an optional "Internal note" field and relabels the old field as "Message on the card", so it is clear that text reaches the customer. Only the label changes, not its behavior.
- **Storage:** the new text is saved in a new column `gift_cards.internal_note` instead of reusing `message`, so the flow that renders the card is untouched. The card page shows it on its own row when filled in.
- **Order history:** issuing a card now also adds an order history entry with the card code and the note, reusing `HistoryEntry`/`HistoryWriter`, so the reason is visible without opening the card. It is non-critical: it runs in a try/catch with a log and is skipped when the note is empty, so issuing the card is never affected.
- **Migrations:** one adds the `internal_note` column (reversible) and another registers the `gift-card-note` entry type, following the convention of earlier entry-type migrations.

## Scope
Flows that do not send the field (checkout and bulk import) behave exactly as before.
--- END EXAMPLE ---

### Example B — fix grouped by data dimension

--- BEGIN EXAMPLE ---
fix(abandoned carts report): resolve owner and order number for restored carts

## Problem
In the Abandoned Carts report, carts restored from a saved session showed no "Owner" (displaying *unassigned*) and no order number, because the follow-up task stayed linked to the original cart. For the same reason, they were missing when filtering by sales rep.

## Changes
- **Filter by rep:** if a cart has no follow-up task of its own, it now uses the one on its original cart. It is ORed with the existing conditions, so it can only return more carts, never fewer.
- **Owner:** taken from the task on the original cart when the cart has none of its own.
- **Order number:** resolved in cascade (cart task → cart checkout → original cart task) instead of depending on the task alone.
- **CSV export:** turns on `use_bom` so Excel shows accented names correctly.
--- END EXAMPLE ---
